## 1. Release thesis under evaluation

The research to date has not demonstrated a missing universal Core/Constitution rule.

It **has** demonstrated a practical gap:

```text
WHAT / WHY semantics exist
+
concrete HOW research exists
+
Host mechanisms exist
!=
adopter can easily find and instantiate a practical HOW
```

Therefore a valid next release may primarily be an **operational architecture release** rather than a constitutional expansion.

```text
NO_NEW_CORE_RULES != NO_RELEASE_VALUE
```

This reconciliation does not yet assign a version number.

## 2. Candidate cargo class A — adopter-facing Operational Architecture

Disposition: `IN_SCOPE_FOR_NEXT_CANDIDATE`

Rationale: this is the direct repair for the practical HOW gap and does not require adopters to activate every reference organ.

Candidate surfaces:

### A1 — operational entrypoint

A release-local operational entrypoint should explain:

```text
problem/cue
-> consequence-first routing
-> WHAT/WHY
-> plural HOWs
-> Host/reference mapping
-> action or honest residual
```

It must explicitly preserve:

- `REFERENCE_HOW != UNIVERSAL_MANDATE`;
- `OPERATIONAL_LIBRARY_SIZE != ACTIVE_CONTEXT_SIZE`;
- non-applicability/lightweight paths;
- Host-local fitness;
- evidence maturity boundaries.

### A2 — compact cue index

Curate the research `CUE-INDEX.md` into an adopter-facing cold/hot routing surface.

Do not ship the entire research map as a required always-loaded prompt.

### A3 — operational HOW map

Curate `OPERATIONAL-ARCHITECTURE-MAP.md` into a release-local HOW map.

The map may be large/cold. Its purpose is discoverability, not mandatory runtime injection.

### A4 — reference pointer/index

Ship a release-local index from operational node/HOW to:

- bundled reference organ;
- bounded procedure;
- Host-native mechanism pattern;
- explicit field/research residual.

The release index must not point adopters to unstable research branch paths for required usage.

## 7. Candidate cargo class F — maintenance/tooling

Disposition: `IN_SCOPE_DECISION_REQUIRED`

### Known inherited false-BLOCK

`releases/current/tools/ena_evolve.py` currently:

- identifies itself as v0.3.5 candidate.2 / state 1.2;
- emits v1 adaptation packets;
- does not fully implement v0.3.6 expression/latent/mutation-pressure/v2 packet semantics;
- requires `--variation-space` on `propose` and `import`, false-blocking valid latent-now/experiment-later use.

Do **not** treat a two-line argparse patch as automatically sufficient.

Compare three HOWs:

#### TOOL-HOW-A — narrow legacy repair

Make `--variation-space` optional and keep explicit legacy/non-v2 status.

Pros: cheap; removes known false-BLOCK.

Cons: tool remains semantically incomplete and may look more Current-compatible than it is.

#### TOOL-HOW-B — deprecate legacy without replacement

Retain/read-only lineage or move the tool out of the primary adopter path.

Pros: avoids misleading runtime surface.

Cons: weakens practical evolution tooling.

#### TOOL-HOW-C — minimal v2-compatible evolution helper

Provide a deliberately small tool that creates/updates/validates Current v2 record/packet structures without requiring early Variation Space and without inventing authority/evidence truth.

Pros: aligns practical tooling with Current and next release's HOW emphasis.

Cons: larger implementation/validation burden; must not duplicate a second semantic engine.

Provisional preference: `EVALUATE_TOOL_HOW_C_FIRST`, with A as fallback only if a truly minimal v2 helper cannot stay bounded.

No Current patch is authorized yet.
