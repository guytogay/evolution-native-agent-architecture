# ENA Handoff Protocol — Workbench Adapter

Status: `ENA_PROJECT_ADAPTER / NOT_CANONICAL_GENERAL_METHOD / NOT_ENA_CURRENT`

General human-AI continuation, deep succession, and fresh-evaluation method is canonically owned by:

`guytogay/human-ai-workbench`

Primary method surfaces:

- `README.md`
- `templates/HANDOFF.md`

ENA uses that method; ENA does not maintain a parallel canonical copy.

## 1. ENA-specific routing

For normal ENA continuation:

```text
main / NOW.md
-> directly relevant ENA artifact or Issue
-> work
```

For a DEEP succession explicitly required by continuity risk:

1. read current `NOW.md`;
2. read `research/handoffs/CURRENT-HANDOFF.yaml`;
3. follow its `start_here` pointer;
4. read only the record surfaces it actually routes to;
5. reverify mutable live facts before material writes;
6. continue without asking the user to reconstruct persisted ENA background.

For a FRESH independent validator:

- do not provide the project-manager handoff;
- use an isolated experimental surface;
- do not reveal ENA research/oracle surfaces and then ask the validator to ignore them.

The generic reason for these context modes belongs to Human-AI Workbench. This file records only how ENA applies them.

## 2. ENA authority hierarchy

When ENA surfaces disagree:

```text
Current identity
  -> releases/current/CURRENT-BASELINE.yaml

Live project/research status
  -> NOW.md on main

Current deep-succession router
  -> research/handoffs/CURRENT-HANDOFF.yaml

ENA-specific required takeover context
  -> research/handoffs/REQUIRED-TAKEOVER-CONTEXT.yaml

Dated handoff record
  -> occurrence/snapshot, not automatically live truth

Historical plans / old branch state / chat
  -> lineage or context unless current routing explicitly depends on them
```

A premerge handoff snapshot may remain historically correct while no longer describing mutable branch state. Preserve occurrence truth rather than rewriting history.

## 3. What stays in ENA

ENA owns its project-specific handoff artifacts, including:

- `CURRENT-HANDOFF.yaml`;
- `REQUIRED-TAKEOVER-CONTEXT.yaml`;
- `research/handoffs/records/<handoff-id>/`;
- ENA-specific project state, research decisions, negative/null results, experiment identities, repo boundaries, and next actions carried by those records.

These are ENA occurrences and adapters, not general project-method authority.

## 4. What belongs in Human-AI Workbench

When ENA reveals a method that can be stated independently of ENA theory or internal project state, canonical ownership should move to Human-AI Workbench.

Examples include:

- NORMAL vs DEEP vs FRESH context modes;
- handoff depth proportional to continuity risk;
- retrieve the smallest missing context rather than full-auditing by default;
- structural isolation for fresh evaluation;
- capture first complete AI output before correction when it is evidence;
- preregister unfavorable/null interpretations;
- retire temporary workspaces after preserving unique material.

ENA may cite or apply these methods but should not keep a second full canonical exposition.

## 5. ENA-specific deep-succession completeness

When ENA genuinely needs DEEP succession, the receiver must be able to determine, from the record plus live readback where needed:

- what version is Current and whether released bytes changed;
- the active ENA research phase;
- recent experimental results including negative/null interpretations;
- which hypotheses were narrowed rather than supported;
- which Coverage Map obligations remain alive;
- the next falsifiable consequential action;
- which related repositories have different responsibilities;
- which old workspaces are historical/delete-safe;
- what should not be rerun merely to seek a preferred result.

This list is ENA-specific project content. The general decision to use DEEP succession and how much context to carry is Workbench method.
