# ENA Project Management Discipline — Workbench Adapter

Status: `ENA_PROJECT_ADAPTER / NOT_CANONICAL_GENERAL_METHOD / NOT_ENA_CURRENT`

General reusable human-AI project-working method is canonically owned by:

`guytogay/human-ai-workbench`

ENA remains a major real-use source and consumer of that method, but should not maintain a duplicate project-management framework.

## 1. ENA-specific project authorities

ENA's live/local authorities remain:

```text
Current adoption identity
-> releases/current/CURRENT-BASELINE.yaml

Live project/research status
-> NOW.md

Research evidence / hypotheses
-> research/...

Current deep-succession router
-> research/handoffs/CURRENT-HANDOFF.yaml

Validation coverage debt
-> research/evolution-inbox/EVOLUTIONARY-MEMORY-VALIDATION-COVERAGE-MAP.md
```

General rules for project continuation, handoff depth, decision recording, temporary-workspace lifecycle, and lightweight AI experiment execution belong to Human-AI Workbench.

## 2. ENA-specific immutable-lineage rule

Frozen/released ENA identities are content-addressed evidence objects, not mutable narration surfaces.

```text
BRANCH HEAD != FROZEN IDENTITY
RELEASED BYTES != EDITABLE PROJECT NOTES
```

Do not modify `releases/current/` in place to improve narration or absorb later research.

Candidate/product defects, oracle defects, validation-infrastructure failures, evidence gaps, and project-state projection drift must remain distinguishable.

## 3. Preserve ENA occurrence truth

A dated ENA handoff record, validator response, failed oracle, experiment output, or branch state records what happened at that time.

Later correction should update live state/method without rewriting the occurrence to make history look cleaner.

Generic occurrence-vs-method practice is Workbench territory. ENA keeps the concrete occurrence because it is project evidence.

## 4. Preserve research possibility while executing one next step

ENA may have one current consequential action without collapsing other research branches.

```text
PLURAL RESEARCH POSSIBILITY SPACE
+
ONE NEXT EXECUTION STEP
```

The Evolutionary Memory Validation Coverage Map is the current explicit debt ledger. A branch may end as supported, narrowed, subsumed, rejected, metaphor-only, or field-unresolved; it may not silently disappear merely because another branch is active.

## 5. Negative/null results are ENA evidence

ENA must preserve negative and null evidence when it changes the research state.

Current examples include:

- A-H: no observed semantic-reachability defect under tested conditions;
- I-L: no observed relative inheritance-mechanism advantage in the saturated Supplier-B fixture;
- stronger boundary-oriented transfer-fitness claim narrowed.

The generic discipline of preregistration and honoring null results is Workbench method. The concrete results and hypothesis dispositions remain ENA research evidence.

## 6. ENA branch/workspace application

ENA currently applies the Workbench temporary-workspace principle as:

```text
main = durable continuation
short-lived branch = temporary isolation/review
cleanroom = experimental surface, not automatic archive
```

Before retiring an ENA branch or cleanroom, preserve unique decision-relevant research/evidence in the appropriate durable repository.

Do not merge a stale branch wholesale merely because it contains one useful artifact.

## 7. Cross-repository ownership

Use the following routing before adding durable material:

```text
Agent evolution theory / mechanism / ENA evidence / Current
-> evolution-native-agent-architecture

General human-AI project-working method
-> human-ai-workbench

Evidence-backed practical ENA operating HOW
-> ena-field-guide

Disposable isolated evaluation substrate
-> validation cleanroom
```

A useful idea should have one canonical owner. Other repositories should reference or locally adapt it rather than copy it.

## 8. Method extraction rule

ENA is expected to continue generating project-working lessons because it is a difficult long-lived human-AI project.

When a lesson no longer depends on ENA-specific theory/state and appears reusable across projects:

```text
ENA occurrence
-> abstract project-general method
-> Human-AI Workbench becomes canonical
-> ENA retains local adapter / occurrence evidence only
```

Do not wait for ENA completion before making this extraction, and do not promote a one-off project trick into Workbench without enough evidence to justify generalization.

## 9. Current ENA admission rule

Project method does not determine ENA natural law.

```text
USEFUL PROJECT METHOD
!=
ENA NATURAL LAW

INTERESTING RESEARCH RESULT
!=
CURRENT CHANGE

PRACTICAL HOW
!=
RESEARCH THEORY
```

ENA Current changes remain downstream of ENA-specific decision-relevant evidence and governed release work.

## 10. Operating invariant

```text
WORKBENCH OWNS HOW WE RUN LONG-LIVED HUMAN-AI PROJECTS
ENA OWNS WHAT ENA IS LEARNING ABOUT VIABLE EVOLVING AGENCY
FIELD GUIDE OWNS HOW TO APPLY VALIDATED ENA-DERIVED PRACTICE
```

Keep these roles coupled by references and feedback, not by duplicated canonical content.
