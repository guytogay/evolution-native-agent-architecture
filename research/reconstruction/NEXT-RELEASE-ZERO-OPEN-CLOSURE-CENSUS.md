## Maintainer acceptance condition

The next ENA release is not ready merely because a candidate passes semantic or machine validation.

At release authorization time all durable research inputs must have a final disposition:

```text
OPEN_GITHUB_ISSUES = 0
OPEN_RESEARCH_PRS = 0
UNRESOLVED_RESEARCH_TOPICS = 0
UNASSIGNED_FIELD_SEEDS = 0
UNASSIGNED_EXTERNAL/COMMUNITY_INSPIRATIONS = 0
UNTRIAGED_KNOWN_DEFECTS = 0
```

This is a **closure** requirement, not a requirement that every idea become a Core rule or universal organ.

Permitted final dispositions include:

- `RELEASE_ABSORBED` — represented in the next release's Core/reference/adoption/process surface;
- `RESOLVED_BY_REFERENCE_ORGAN` — concrete HOW exists with truthful evidence boundary;
- `RESOLVED_BY_EXISTING_PROPERTY` — no additive semantic change needed, with the operational landing made explicit;
- `TOOLING_FIXED` — implementation defect repaired and regression-guarded;
- `PROCESS_FIXED` — project/release/adoption process ambiguity resolved;
- `EXPLICIT_SCOPE_BOUNDARY` — ENA intentionally does not claim/solve the broader question, and the boundary itself is closed and usable;
- `REJECTED_NOT_ENA` — proposal would add unsupported ontology/burden or belongs to an external institution/Host;
- `RETIRED_REDUNDANT` — duplicate/superseded path removed after its useful content is preserved;
- `SUPERSEDED_WITH_EVIDENCE_PRESERVED` — historical tracker/branch is closed without rewriting occurrence truth.

Not permitted as release-time terminal states:

- `OPEN`;
- `TBD`;
- `DEFER`;
- `DISCUSS_LATER`;
- `DELIBERATELY_UNRESOLVED` without an explicit ENA scope boundary;
- `FIELD_OBSERVATION_NEEDED` when the release claim still depends on that observation.

A question may remain empirically unproven only when the release explicitly **does not make the stronger claim** and the absence of that proof has a closed, truthful applicability boundary.

> Zero open does not mean pretending omniscience. It means no known question is left without a governed disposition.

# F. Release closure algorithm

## Phase 1 — census and deduplication

1. enumerate open Issues and PRs;
2. harvest Issue comments, seed registers, external HOW notes, field reports, and research artifacts;
3. deduplicate by failure mechanism/property without deleting provenance;
4. map every source to #90–#94 or an explicit non-ENA boundary.

## Phase 2 — operational closure

For each topic:

```text
WHAT -> WHY -> HOW -> EVIDENCE -> FINAL DISPOSITION
```

and:

```text
PROPERTY | ORGAN | HOST_BINDING | EVIDENCE | ADOPTION
```

Not every axis must be globally proven. But every unproven axis must be irrelevant to the release claim or represented as a closed applicability/claim-strength boundary.

## Phase 3 — source-Issue closure

Close source Issues only after their surviving content has a durable landing. Closing an Issue is evidence of administration only; it is never evidence that the underlying mechanism works.

## Phase 4 — candidate/release preparation

Only after the research graph has no unresolved known input should a release candidate be frozen.

A release candidate may still be independently falsified and require repair; such new findings are added to the census and must also close before release.

## Phase 5 — reverse release audit

Immediately before release authorization, re-run:

- open Issue search;
- open PR search;
- seed/comment/inspiration harvest;
- TODO/TBD/DEFER/OPEN research-state search where practical;
- known residual manifest readback;
- release Current/reference/adoption/tooling mapping;
- exact-head CI and independent-validation state.

Required final report:

```text
OPEN_ISSUES = 0
OPEN_PRS = 0
UNRESOLVED_TOPICS = 0
UNASSIGNED_INSPIRATIONS = 0
UNTRIAGED_DEFECTS = 0
KNOWN_SCOPE_BOUNDARIES = <explicit list, not hidden debt>
```

This report does not authorize release by itself. Maintainer authorization and normal immutable release/freeze discipline still apply.

# G. Anti-cheating rules

The zero-open objective must not be gamed by:

- closing Issues with “future work” still inside them;
- moving unresolved items into a new catch-all backlog;
- calling a field hypothesis solved because no counterexample was observed;
- turning unknown external truth into a schema PASS;
- deleting research branches before their unique mechanisms/provenance are absorbed;
- merging all concepts into vague prose that leaves no HOW;
- forcing all inspirations into Core merely to claim absorption;
- manufacturing experiments whose only result is expected diversity;
- using a release deadline as evidence.

> **No backlog laundering. No ontology laundering. No evidence laundering.**

> **A release is closed when every known question has a truthful home, not when every question has the answer the architecture hoped for.**
