# ENA Living Evolution Loop

Status: `CANDIDATE / PROJECT_PROCESS / NOT_MAINLINE`

## Premise

Every Agent that uses ENA can be a field node in ENA's own evolution.

The field node is not an automatic maintainer, reviewer, or promotion authority. It is a source of situated evidence and variation.

## Loop

```text
ENA release/profile
    -> field use
    -> incident / near miss / friction / value / variation
    -> contribution
    -> reconciliation
    -> experiment / evidence
    -> candidate change
    -> authorized adoption
    -> next release/profile
```

ENA therefore becomes a living project with feedback rather than a static governance document.

## Field-node duties

A field node SHOULD contribute when it observes a material false or unsupported consequential claim; recovery failure or history-loss risk; triggered obligation that was forgotten or noisy; governance mechanism that prevented real harm; governance mechanism that repeatedly adds cost without changing decisions; portability failure; model/route-specific behavior relevant to capability or authority; counterexample to an ENA assumption; new lower-cost implementation pattern; or new variation that may improve viable agency.

## Contribution boundary

A field node may propose evidence, interpretation, candidate change, host pattern, rejection, simplification, retirement, or new research questions.

It may not infer Mainline acceptance, global truth from local experience, promotion authority, or implementation authority outside its mandate.

## Cross-host selection

Repeated independent observations increase research priority, not automatic correctness.

Selection should examine recurrence across hosts/models/tasks, consequence severity, observed prevention/recovery value, friction and cost, false positives, portability, evidence independence, and whether an existing Mainline semantic already explains the incident.

## Privacy / minimization

Field contributions should include enough context to make evidence applicable without needlessly copying private user content, credentials, secrets, or unrelated operational data.

## Project health

The ENA project itself should observe contribution throughput, reconciliation latency, stale unresolved items, field-to-fix cycle time, repeated rediscovery, project governance overhead, and whether Mainline semantic complexity grows slower than failure coverage.

The project should be willing to simplify or retire mechanisms that no longer pay rent.
