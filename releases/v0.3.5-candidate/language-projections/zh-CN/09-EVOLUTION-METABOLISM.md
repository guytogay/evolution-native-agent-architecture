# 9. 进化代谢

这份文件把“主动促进进化”变成可以真正执行的流程。

它是参考机制，不要求所有 Host 长成同一种器官。

## 1. 十个功能

一个比较完整的进化系统需要：

1. **观察**：收集纠正、失败、摩擦、矛盾、成功、环境变化、新能力、新机会；
2. **唤醒**：让这些信号获得复查机会；
3. **产生变异**：形成一个或多个明确变化候选；
4. **实验**：让候选在合适的变异空间里接触现实；
5. **评估**：记录真实结果和代价；
6. **选择**：保留、本地修改、重试、拒绝或继续未知；
7. **整合**：在真实授权和后果允许时，把被选择的适应进入长期/共享状态；
8. **淘汰/整理**：把失效、陈旧、有害或冗余适应移出活跃状态；
9. **迁移/重组**：把有效适应分享给其他 Agent，或与其他适应组合；
10. **再次循环**：已经保留的适应会改变下一次搜索空间。

缺少某个功能没关系，但不能假装它已经存在。

## 2. 唤醒机制

事件触发可以包括：

`用户纠正 | 重复失败 | 摩擦 | 矛盾 | 重复成功 | 能力变化 | 环境变化 | 新机会 | 适应陈旧`

周期/空闲复查是防止慢性问题永远没人发现的补漏机制。

ENA 不规定统一周期。

**定时器触发复查，不触发强制修改。**

## 3. 变异空间

核心问题是：

> 在哪里可以让一个“不知道好不好”的变化真正跑起来？

可以是：

- 分支；
- 沙箱；
- 测试 Agent；
- 一次性 VM/容器；
- 影子执行；
- 小范围试运行；
- 可恢复本地配置；
- 独立 skill 版本。

它要尽量说明：

- 允许改什么；
- 谁承担后果；
- 哪些影响会跑出实验范围；
- 怎么恢复/清理；
- 哪些对外授权仍然必须另外成立。

## 4. 候选记录

一个好的候选至少说清：

- 什么信号触发了它；
- 假设；
- 想改什么；
- 预期什么变化；
- 在哪里试；
- 可能影响谁；
- 当前环境是什么；
- 还不知道什么；
- 怎么观察结果。

不要求提前证明“它一定是好的进化”。

## 5. 选择

把真实结果分维度记录：

`变好 | 变差 | 不变 | 未知`

一个候选可能同时有好有坏。

选择状态：

`SUPPORTED | PARTIAL | NOT_SUPPORTED | HARMFUL | UNKNOWN`

被淘汰的候选仍然是未来学习资料。

当前赢家也没有权力禁止以后出现新变异。

## 6. 整合与权限

实验成功不等于自动可以进入长期/生产/共享状态。

因为整合本身可能跨过新的后果和授权边界。

在真实本地授权范围内，Agent 可以自主整合自己的内部结构变化。

但修改自己权限表不能凭空产生对外授权。

## 7. 整理和遗忘

进化不是无限往自己身上堆东西。

可以有：

`ACTIVE → DORMANT → ARCHIVED → RESTORED / RETIRED`

判断依据可以包括实际使用、真实价值、冲突、维护负担、是否被更好方案替代等。

“很久没用”不能单独证明它应该被永久删除。

用户写的、外部安装的、受保护的内容，不能因为 Agent 有写权限就自动纳入自主整理。

## 8. 迁移包

迁移时尽量带上：

- 改了什么；
- 为什么；
- 来源 Host / 模型 / 语言 / 配置；
- 证据；
- 哪些变好；
- 哪些变差；
- 哪些未知；
- 依赖条件；
- 授权假设；
- 已知失败模式；
- 不知道能不能迁移的部分。

接收方只把它当迁移候选。

优先检查来源和接收方之间真正可能影响结果的差异，不必重复整个发明过程。

## 9. 重组与涌现

A 有效、B 有效，不代表 A+B 只是两者相加。

可能冲突、抵消、放大，甚至出现全新的能力。

正向涌现也应该像失败一样被正式记录。

## 10. 参考工具

`tools/ena_evolve.py` 提供：

`init / observe / review / propose / experiment / evaluate / integrate / archive / export / import / closure / status / selftest`

这个工具只记录和组织进化过程，不直接替 Agent 执行任意自我修改，也不制造外部授权。

Host 可以改它、替换它，甚至做得比它好。

**不要崇拜工具；让工具自己也能进化。**
