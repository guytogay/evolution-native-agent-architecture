## Hypothesis

The Persistent Project Collaboration Protocol may be more than project-management infrastructure. It may function as an **external evolution substrate** for ENA-like agents by making variation, evidence, reconciliation, inheritance, recovery, and decision lineage persist independently of one transient model/session/runtime.

Working research label only:

`Persistent Evolution Substrate`

This label is **NOT** ENA terminology, **NOT** a new Capability, and **NOT** a Constitution candidate at this stage.

## Why this may matter in a single-Agent world

A nominally single Agent that continues across sessions, context windows, restarts, restores, model versions, or host epochs is temporally distributed.

Past-self, current-self, and future-self do not necessarily share reliable hidden cognitive state. A persistent project substrate can allow those temporally separated instances to inherit:

- previous variation/proposals;
- evidence and counterevidence;
- failed experiments;
- unresolved conflicts;
- reconciliation outcomes;
- authority/decision lineage;
- recoverable release state;
- known unknowns.

This suggests a possible distinction:

`memory of prior content != inheritable evolution state`

A durable evolution substrate may preserve not merely what happened, but why a candidate existed, what evidence supported or rejected it, which decisions were authorized, and what remains unresolved.

## Why this may matter in a multi-Agent society

Heterogeneous participants can generate independent variation without requiring one shared runtime or hidden context:

- ChatGPT
- Gemini
- Hermes Agent
- OpenClaw
- DeepSeek Harness
- Codex
- humans
- bots/automation

The collaboration substrate can then support a loop of:

`Variation -> Evidence / Experiment -> Reconciliation / Selection -> Authorized Adoption -> Persistent Inheritance`

This structure is compatible with the ENA direction:

- `Variation autonomous; authority governed.`
- `Protocol-level unity + cognitive diversity.`

## Candidate structural interpretation

The protocol may externalize parts of an evolutionary loop:

1. **Variation** — independent contribution artifacts.
2. **Selection pressure** — evidence, experiments, HAR, counterexamples.
3. **Selection/reconciliation** — explicit comparison against current project reality.
4. **Authority boundary** — reconciliation does not automatically imply implementation/promotion.
5. **Inheritance** — Mainline, releases, decisions, evidence, and unresolved candidate state remain recoverable for future participants.
6. **Recovery continuity** — a participant/runtime may disappear while project lineage remains discoverable.

If this interpretation survives testing, Agent continuity may depend less on continuous internal memory and more on a legible, externally inheritable evolution state.

## Important unknown

What exactly constitutes the continuity-bearing state of an ENA organism?

Possible components include:

- history;
- evidence;
- authority lineage;
- decisions;
- recoverable state;
- unresolved variation;
- current projection/index state;
- implementation/runtime state.

No claim is made that a Git repository, Drive folder, memory store, or Host alone is the organism.

## Falsification pressure

Before promotion, attack the substrate itself:

- Can `PROJECT-HUB.md` become stale and create false current-state confidence?
- Can one participant propose and reconcile its own contribution, producing self-confirmation?
- Can GitHub and Drive diverge into two incompatible project realities?
- Can the Inbox grow until salience/retrieval fails?
- Can Reconciliation be mistaken for Promotion Authority?
- Can Project Hub/Registry become a projection whose truth semantics exceed its source state?
- Can bridge nodes silently alter contribution meaning?
- Does the protocol improve actual adaptation, or only documentation quality?
